# RMUX Integration - Deferred Features

This document tracks features that were intentionally deferred from the V1 RMUX integration but are designed to be added incrementally in future work.

## V1 Scope (Complete)

The V1 implementation includes:
- Embedded daemon lifecycle management
- Client wrapper with daemon handle and pane_id capture
- Event loop with pane_id tracking and event emission
- Terminal manager with lazy peer registration
- Pane allocator for stable naming
- RMUX-by-default for new local panes
- Manual RMUX pane creation via command palette
- Snapshot structure and creation (in-session restoration)
- Restoration logic (tab/window moves within live session)
- Cleanup on detach

## Deferred Features

### 1. EventLoopEvent Subscription

**Status:** Events emitted but not consumed

**Details:**
- `EventLoop` emits `EventLoopEvent::Connected { pane_id }` and `EventLoopEvent::Disconnected`
- No code in the application subscribes to these events
- Events are generated by the event loop but ignored

**Why Deferred:**
- V1 pane lifecycle works without event-driven reactions
- The event loop handles connection, render updates, and shutdown internally
- Event subscriptions would be useful for:
  - UI notifications when pane connects/disconnects
  - Triggering peer registration on connection (currently uses lazy registration)
  - Logging or telemetry on pane lifecycle events

**Future Implementation:**
```rust
// Example: Subscribe to EventLoop events from a view or model
ctx.subscribe_to_model(&event_loop, |me, _handle, event, ctx| {
    match event {
        EventLoopEvent::Connected { pane_id } => {
            // React to connection
        }
        EventLoopEvent::Disconnected => {
            // React to disconnection
        }
    }
});
```

### 2. Peer Communication Usage

**Status:** Module complete but unused in application code

**Details:**
- `MessageQueue` singleton with in-process storage
- `RmuxPeer` handle with register/unregister/list peers
- Message queuing with 1MB payload limit
- Comprehensive test coverage in `peer.rs`
- `terminal_manager.peer()` method exists but is never called
- Lazy registration via `ensure_peer_registered()` is implemented but never triggered

**Why Deferred:**
- V1 scope is single-pane operation
- Inter-pane messaging is a separate feature requiring:
  - UI for sending messages between panes
  - Integration with AI agents or other pane types
  - Message format and protocol design
  - Security and permission model for inter-pane communication

**Future Implementation:**
```rust
// Example: Send message from one pane to another
let manager = terminal_manager.as_mut(ctx);
if let Some(peer) = manager.peer(ctx) {
    peer.send_message(target_pane_id, b"hello".to_vec())?;
}

// Example: List available peers
let peers = peer.list_peers();
for peer_info in peers {
    println!("Pane {}: {}", peer_info.pane_id, peer_info.session_name);
}
```

### 3. External Pane Attachment

**Status:** Ownership variant exists but never used

**Details:**
- `RmuxPaneOwnership::ExternallyAttached` enum variant exists
- Only `WarpCreated` panes are ever created in the codebase
- No UI or code path for attaching to external RMUX sessions
- Cleanup logic handles both ownership types, but only one is used

**Why Deferred:**
- V1 scope is Warp-owned panes only
- External attachment would require:
  - UI for selecting/connecting to external RMUX sessions
  - Session discovery mechanism (list available sessions)
  - Authentication/authorization for external sessions
  - Different lifecycle semantics (detach vs close)

**Future Implementation:**
```rust
// Example: Attach to external RMUX session
let spec = RmuxPaneSpec::new(
    "external-session-name",
    RmuxPaneOwnership::ExternallyAttached,
);
let (view, manager) = RmuxTerminalManager::create_model(spec, ...);
```

### 4. Stable Session Naming for Agent Panes

**Status:** Uses UUID fallback when base command unknown

**Details:**
- `pane_allocator::allocate_rmux_session_name(None)` returns UUID: `format!("warp-{}", uuid)`
- Stable naming like "codex-1", "codex-2" requires base command context
- Current naming is functional (UUIDs work) but not semantic
- Agent launch context is not available at pane creation boundary

**Why Deferred:**
- Naming is functional for V1 (UUIDs work correctly)
- Stable naming requires:
  - Agent context integration at pane creation
  - Passing agent type/command name to pane allocator
  - Coordination with agent team mode and multi-agent workflows

**Future Implementation:**
```rust
// Example: Stable naming with agent context
let session_name = pane_allocator::global_allocator()
    .allocate_rmux_session_name(Some("codex")); // Returns "codex-1"
```

## Persistence Design Decision

RMUX panes are marked as **non-persisted** in `app_state.rs`:
```rust
| LeafContents::RmuxTerminal(_) => false,
```

**Rationale:**
- Restoration only within live session (moving panes between tabs/windows)
- Not across app restart
- External daemon may not survive app restart
- Cross-restart restoration would require daemon persistence and reconnection logic

This is intentional per V1 design and may be enhanced in future work.

## Implementation Notes

### Architecture Supports Incremental Enhancement

The deferred features are designed to be added without blocking V1:
- EventLoop events are already emitted (just need subscribers)
- Peer module is complete and tested (just needs usage integration)
- Ownership enum supports both types (just needs external attachment UI)
- Pane allocator supports stable naming (just needs agent context)

### Testing

All deferred features have test coverage:
- `peer.rs` has comprehensive unit tests
- EventLoop event emission is tested indirectly via connection tests
- Pane allocator has tests for stable naming patterns

### Compilation Status

All code compiles successfully:
```bash
cargo check -p warp --features rmux_native_pane
```

Warnings are non-critical (unused imports, dead code in other modules).
